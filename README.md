# GTag Display — nRF52840 + Home Assistant

Экран LCD 256×128 от электронного ценника G-Tag подключён к плате
nRF52840 Pro Micro / nice!nano. Home Assistant передаёт кадр через BLE,
прошивка проверяет CRC32 и выводит изображение после отключения клиента.

В проекте одна целевая прошивка:
[nrf-gtag-display.yaml](config/esphome/nrf-gtag-display.yaml) с компонентом
[gtag_display](config/esphome/components/gtag_display).
Интеграция HA находится в [custom_components/gtag_ble_test](custom_components/gtag_ble_test).
Её техническое имя сохранено для совместимости с уже добавленными устройствами
и идентификаторами сущностей; в интерфейсе она называется **GTag Display**.

Версия **0.6.0** позволяет выбрать готовый макет и сущности через настройки HA,
посмотреть результат и применить его. Произвольные экраны доступны через действие
`gtag_ble_test.draw` с шаблонами, текстом, фигурами и иконками.

![Пример макета «Время и два показателя»](docs/screen-clock-two.png)

Для распространения выбран **HACS**. Локальная структура подготовлена:
`custom_components/` в корне, `hacs.json`, переводы, иконка и автоматические тесты.
Публичный GitHub-репозиторий пока не создан, поэтому сейчас устанавливайте ZIP
или копируйте каталог вручную. [Установка и подготовка публикации](docs/installation.md).

## Подключение

| Сигнал LCD | GPIO nRF52840 |
|---|---|
| DIO | P0.11 |
| CLK передачи данных | P1.04 |
| CS | P1.06 |
| RESET | P1.13 |
| DisplayCLK / S1 | Штатная плата ценника, около 28,8 кГц |

Штатные питание LCD и тактирование DisplayCLK должны сохраняться постоянно.
Наличие штатного тактирования подтверждено для этой сборки. Описание платы
`adafruit_itsybitsy_nrf52840` используется как основа сборки; её лишние
периферийные устройства отключены. Сохраняются `dcdc: false` и профиль
загрузчика `adafruit_nrf52_sd140_v6`.

## Ожидание и BLE

Используется **System ON idle**: Zephyr останавливает CPU между работой потоков
и прерываниями, сохраняя RAM, GPIO и обслуживание Bluetooth. События подключения,
отключения и принятого кадра пробуждают компонент. Паузы инициализации LCD
и повторные попытки запуска рекламы обслуживаются таймерами.

- Главный цикл ESPHome в простое просыпается раз в секунду для служебной работы;
  BLE-события и таймеры могут разбудить его раньше. Компонент LCD не опрашивается.
- BLE-реклама по умолчанию раз в секунду. Устройство доступно для подключения;
  обнаружение зависит также от сканирования адаптера HA.
- После COMMIT клиент читает STATUS и отключается. На время записи в LCD реклама
  приостановлена, затем запускается снова. Автоматический перезапуск рекламы
  стеком отключён, чтобы новое подключение не пересекалось с выводом кадра.
- USB CDC, UART и логирование в основной конфигурации выключены.
- Задержка после RESET — **50 мс**. Стартовая пауза 3 с и команды LCD сохранены.

System OFF здесь не используется: он лишил бы устройство возможности принимать
подключения BLE. LCD продолжает работать от штатного тактирования.
При проверке на реальном устройстве пользователь измерил потребление
в режиме ожидания **около 50 мкА**. Этот результат признан приемлемым.

```yaml
gtag_display:
  tx_power: 0                 # 0, 4 или 8 dBm
  advertising_interval: 1s   # 100ms..10240ms; 500ms для более частой рекламы
  boot_test_pattern: none    # none, white, black, checkerboard, stripes
```

Тестовый рисунок выводится один раз после запуска, затем устройство ждёт BLE.
При `none` остаётся обычная инициализация с очисткой экрана. Для диагностики
можно раскомментировать `logger` в том же YAML — это также включит USB CDC.
Измерять экономичное ожидание следует с основной конфигурацией без логирования.

## Сборка и Home Assistant

Конфигурация рассчитана на **ESPHome 2026.8.2**, **nRF Connect SDK 2.9.2**.
Установка и сборка из корня проекта (Python 3.12+, первая сборка скачивает SDK):

```sh
python3 -m venv .venv
.venv/bin/pip install esphome==2026.8.2
.venv/bin/esphome config config/esphome/nrf-gtag-display.yaml
.venv/bin/esphome compile config/esphome/nrf-gtag-display.yaml
```

UF2 появляется в
`config/esphome/.esphome/build/nrf-gtag-display/.pioenvs/nrf-gtag-display/zephyr/zephyr.uf2`.
В основной прошивке USB-порт отсутствует: вход в уже установленный загрузчик
выполняется аппаратным Reset, обычно двойным нажатием. Профиль загрузчика
должен соответствовать конкретной плате.

1. Скопируйте каталог `custom_components/gtag_ble_test` целиком, включая
   `fonts`, в `/config/custom_components/` Home Assistant и перезапустите HA.
2. Используйте Bluetooth-адаптер или прокси с поддержкой активных BLE-подключений.
3. Добавьте обнаруженный **GTag Display** через настройки интеграций.
4. Откройте **Настроить** у записи интеграции: выберите «Время и два показателя»,
   укажите сущности, проверьте предпросмотр и нажмите «Применить».
5. Для теста без датчиков выберите макет «Часы и дата» или включите **Clock screen**
   на странице устройства. Время берётся из HA, обновляется каждую минуту.
6. Откройте **Display preview** и **Last display update** для проверки передачи.

При обновлении с версий 0.4/0.5 достаточно заменить каталог интеграции и
перезапустить HA. Удалять устройство и заново прошивать nRF52840 не требуется.
Идентификаторы прежних сущностей сохранены. Готовый архив собирается командой
`python3 scripts/package.py` в `dist/gtag-ha-integration.zip`; его содержимое
нужно распаковать в `/config/` HA. Скрипт включает шрифт и обновляет `SHA256SUMS`.

Переключатель **Virtual LED** проверяет обмен GATT, меняя флаг в RAM устройства;
физическим светодиодом он не управляет. Он использует ту же блокировку операций,
что и отправка кадра.

Интеграция **0.6.0** также предоставляет:

- Диалог настройки на русском и английском: «Часы и дата», «Один крупный
  показатель», «Время и два показателя». Выбор сущностей, подписи и единицы,
  предпросмотр до отправки и минимальный интервал обновления 5–3600 секунд.
  Длинный текст уменьшается по размеру, а при необходимости сокращается.

- Действие **`gtag_ble_test.draw`**: текст с кириллицей, шаблоны HA, линии,
  прямоугольники и пять встроенных иконок. Шаблоны могут отслеживать время
  и изменения датчиков. Последний макет и режим часов сохраняются после
  перезапуска HA.
- **Refresh display** для принудительной повторной отправки, **Display transfer**
  со статусом и ошибкой, предпросмотр последнего успешно переданного кадра.
- Очередь, объединяющую ожидающие обновления, настраиваемый интервал от 5 секунд
  между завершением передачи и началом следующей и пропуск одинаковых кадров.
- Прежнюю кнопку **Send RLE test image** с рисунком «RLE OK».

[Примеры экранов, описание действия и автоматических обновлений](docs/screens.md).
Для теста достаточно переключателя часов. Частые обновления увеличивают среднее
потребление: измеренные 50 мкА относятся к ожиданию между передачами.

## Протокол и проверки

Кадр — 4096 байт, `row-lsb`: байт `y*32 + x/8`, бит `x%8`, 1 — белый.
Передача: BEGIN → DATA(offset, payload) → COMMIT → STATUS. Поддерживаются
RAW и WHITE_RLE_V1, CRC32 исходного кадра, повтор пакетов, продолжение после
обрыва и переход с Write Without Response на подтверждаемые записи.
Повторный COMMIT не вызывает лишней перерисовки.

UUID сохранены: сервис `7a1e0011-6b5b-4f6d-8d6e-0f4f47544147`,
характеристики с префиксами `7a1e0012` (флаг), `7a1e0013` (данные),
`7a1e0014` (статус), `7a1e0015` (управление). Статус COMPLETE подтверждает
проверку кадра в RAM; отдельного подтверждения видимого изображения нет.

Регрессионные проверки требуют Python 3.11+ и g++, без HA и SDK:

```sh
python3 -m unittest discover -s tests -v
```

Тесты компилируют настоящий C++-драйвер с моделями GPIO, BLE и планировщика,
подают пакеты настоящего Python-отправителя и сравнивают все 8272 слова LCD
с исходной записью ESP32. Проверяются ожидание без опроса, таймеры, повторный
запуск рекламы, диагностические рисунки, повреждённый кадр и восстановление
передачи. Эти тесты не измеряют физические фронты, радиосвязь или ток.
Подробности: [исходная проверка протокола LCD](docs/lcd-protocol-review.md).

Отрисовка и интеграция дополнительно проверены 35 тестами в **Home Assistant 2026.9.2**.
Для этого нужен отдельный Python 3.14:

```sh
python3.14 -m venv /tmp/gtag-ha-tests
/tmp/gtag-ha-tests/bin/pip install -r tests/requirements-ha.txt
/tmp/gtag-ha-tests/bin/python -m pytest tests/ha
```

Здесь используются настоящие движок шаблонов, реестры, действия, хранилище
и платформы сущностей HA; подменена передача по физическому BLE.
Проверяются упаковка всех пикселей, кириллица, смена минуты/даты, обновления
шаблонов, очередь, ограничение частоты, сохранение рабочего предпросмотра
при ошибке и выгрузка интеграции. Запускайте две группы тестов отдельными
командами: тесты C++-драйвера используют лёгкие заглушки модулей HA.
Тесты настройки проходят через настоящий менеджер options flow: отмена,
предпросмотр, применение, смена макета, переводы и сохранение после перезапуска.

Проверено 17 сентября 2026: полная сборка основной прошивки в UF2
(Flash 166 620 байт, RAM 40 200 байт), 11 тестов, включая 12 сценариев
Python → C++ для двух кодеков и восстановления связи. Диагностическая
конфигурация с logger и шахматным рисунком прошла генерацию кода.
После программных проверок пользователь установил UF2 на физическую плату
и подтвердил корректную работу устройства.

Интеграция HA 0.5.0 с отрисовкой экранов, часами и предпросмотром
(коммит `5eeae9a`) также проверена пользователем на реальном устройстве:
подтверждена корректная работа после установки обновления.
