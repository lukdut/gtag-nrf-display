**Проверка протокола LCD по записи ESP32 — 17 сентября 2026**

После этой проверки ожидание после RESET в `gtag_display` уменьшено с 2000
до 50 мс по запросу пользователя. Приведённые ниже измерения и SHA-256
описывают исходную версию до этого изменения.

После объединения проекта целевой конфигурацией стала
`config/esphome/nrf-gtag-display.yaml`, а старые тестовые компоненты сохранены
в initial commit `faeddc2`. Компонент переведён на ожидание событий System ON.
Повторяемая проверка `python3 -m unittest discover -s tests -v` компилирует
полный текущий драйвер с моделями периферии и сверяет все 8272 слова с исходным
файлом ESP32. Приведённый далее отчёт относится к первоначальной проверке.

В текущем `gtag_display` не обнаружено ошибок команд, формата слов, адресации
или передачи видеопамяти относительно `esp32-diagram/ESP32-gtag.sal`.
Оснований исправлять эти части драйвера по результатам сравнения нет.
Прошивка не изменялась. Пользователь подтвердил, что штатное тактирование
DisplayCLK/S1 сохранено.

Проверен компонент `config/esphome/components/gtag_display`, который подключён
в `config/esphome/nrf-bthome-test.yaml`. Вывод не распространяется автоматически
на старые тестовые компоненты `gtag_ble_test` и `lcd_standalone`.

**Как выполнена проверка**

- Разобраны исходные цифровые данные `.sal`, а не только PNG со скриншотом.
  Частота дискретизации — 12 МГц; разрешение по времени — 83,33 нс.
  Каналы: D2=DisplayCLK, D3=CLK, D4=CS, D5=RESET, D7=DIO.
- У всех блоков проверены непрерывность границ, сумма длительностей RLE,
  допустимость начального уровня и полное чтение файла. В записи 79 486 976
  отсчётов на канал. При разборе внутреннего формата использованы
  [описание и реализация sigrok2sal](https://github.com/nemanjan00/sigrok2sal/blob/master/sigrok2sal.py).
  В этой записи версия внутреннего формата — 4; соответствие структуры
  проверено указанными инвариантами. Это не формат бинарного экспорта Saleae.
- Декодирование начинается после последнего импульса RESET. Более ранние
  переходы при запуске ESP32 не трактуются как команды LCD.
- Под каждым активным CS проверено ровно девять положительных фронтов CLK.
  Получено 8272 слова, ошибочных транзакций — 0; команд — 38.
- Из текущего C++-файла взяты без изменений константы, таблица GPIO и методы
  LCD от `wait_()` до `service_lcd_()`. Они скомпилированы на хосте с
  `g++ -std=c++17 -Wall -Wextra -Werror`. Регистры GPIO, часы, логирование и
  watchdog заменены инструментированными заглушками; BLE и запуск Zephyr
  в этой проверке не выполнялись.
- В драйвер подан тот же кадр, который содержится в записи ESP32. Полученная
  программная трасса совпала со всеми **8272 парами D/C + байт**, включая
  очистку, инициализацию и весь кадр. В программной трассе также ровно девять
  положительных фронтов CLK на каждую транзакцию CS.

Временная модель учитывает явные `k_busy_wait()` и миллисекундные переходы
состояний. Она не измеряет исполнение инструкций на nRF52840, прерывания,
электрические фронты и накладные расходы Zephyr.

**Совпавшая последовательность**

| Этап | Запись ESP32 и текущий драйвер |
|---|---|
| Формат слова | 3-wire, CS активен LOW; D/C первым, затем 8 бит MSB-first |
| D/C | 0 — команда, 1 — данные |
| CLK | LOW между словами; данные выставлены до положительного фронта |
| Выход из сна | `11` |
| Очистка | Для адресов `0000`, `0100`, …, `0F00`: `2A`, старший и младший байты адреса, `2C`, 256 байт `FF` |
| Настройка 4C | `4C 0C 00 00 00` — именно **четыре** байта данных |
| Настройка 4D | `4D FF 00 7F` |
| Настройка 4E | `4E 60` |
| Вывод кадра | `2A 00 00`, `2C`, 4096 байт; CS поднимается между 9-битными словами |

Инициализация занимает 4172 слова; последующая запись кадра — 4100 слов.
В записи нет отдельной команды `29` или дополнительного запуска обновления
после последнего байта. Добавлять их для соответствия этому примеру не нужно.
Не нужно также удерживать CS LOW на протяжении всех 4096 байт: рабочий пример
поднимает CS после каждого слова, как и текущий драйвер.

**Временные параметры**

| Параметр | Измерено у ESP32 | Текущий драйвер |
|---|---|---|
| Последний RESET LOW | 52,917 мкс | Явная задержка 50 мкс плюс время операций GPIO |
| RESET HIGH → первый CS команды `11` | 49,927 мс | Задано около 2000 мс |
| CLK HIGH внутри слов | минимум/медиана 1,667 мкс; максимум 65,083 мкс | Задана задержка 2 мкс плюс время исполнения |
| CLK LOW между битами слова | минимум/медиана 1,833 мкс | Задана задержка 2 мкс плюс время исполнения |
| Период CLK внутри слова | минимум 3,500 мкс; медиана 4,250 мкс | Номинально 4 мкс плюс время исполнения |
| CS LOW → первый CLK HIGH | минимум/медиана 3,417 мкс | Две задержки по 2 мкс плюс время исполнения |
| Последний CLK LOW → CS HIGH | минимум 1,583 мкс; медиана 2,333 мкс | Задана задержка 2 мкс плюс время исполнения |
| CS HIGH между словами | минимум 1,833 мкс; медиана 1,917 мкс | Задана задержка 2 мкс плюс время исполнения |
| Очистка → `4C` | 9,936 мс | `wait_(…, 10)` |
| Последний байт `4C` → `4D` | 3,799 мс | `wait_(…, 4)` |
| Последний байт `4D` → `4E` | 0,833 мс | `wait_(…, 1)` |
| Последний байт `4E` → адрес кадра | 501,094 мс | `wait_(…, 500)`, затем ожидание кадра и отключения BLE |
| Адрес и полный кадр | 171,573 мс | В модели без накладных расходов — 172,198 мс; физически не измерено |

`wait_()` использует целые миллисекунды, поэтому фактическая пауза может быть
короче указанного числа почти на 1 мс либо удлиняться планировщиком. Например,
в модели паузы между настройками получились 3,792 и 0,834 мс — близко к записи
ESP32. Значения из таблицы описывают рабочий пример, а не документированные
пределы контроллера LCD: по одной записи нельзя установить минимально
допустимые задержки или максимальные паузы.

Основное отличие — более долгое ожидание после RESET. По записи не выявлено
оснований считать его ошибкой; оно увеличивает время запуска примерно на
1,95 секунды. Сокращение этой задержки — отдельная оптимизация, не необходимое
исправление протокола. Интервалы SPI не обязаны быть абсолютно равномерными:
в самой рабочей записи встречаются удлинённые импульсы.

**DisplayCLK и изображение**

После запуска DisplayCLK в записи непрерывен. Во время работы LCD период
составляет 414–419 отсчётов, медиана 417: это примерно 28,8 кГц.
Генерация этого сигнала в nRF-драйвере отсутствует. При подтверждённом
пользователем сохранении штатного тактирования добавлять её не требуется.
Назначение S1 как входа DisplayCLK также описано в
[исследовании G-Tag 6 из README](https://gist.github.com/bttrem/30eefce2549c1a873f382b5cbdcb3541).

Кадр из записи точно восстанавливается как сетка с шагом 16 пикселей,
границей и диагоналями при упаковке `row-lsb`: индекс байта `y*32 + x/8`,
бит `x%8`, 1 — белый. Проверено совпадение всех 4096 байт с этим рисунком.
При развороте битов внутри байта диагонали распадаются на фрагменты.
Это согласуется с упаковкой текущей интеграции HA. Само видимое изображение
на физической панели в этой проверке не наблюдалось.

**Предел вывода**

Исправления цифрового протокола относительно предоставленного рабочего
примера не обнаружены. Физические уровни, реальные задержки nRF52840 и
устойчивость к прерываниям можно окончательно сопоставить только по аналогичной
записи с текущей платы. Побайтовое совпадение программной трассы не подменяет
эту аппаратную проверку.
