# Значок устаревших данных

Начиная с 0.9.0-beta.3 плата сама отслеживает срок актуальности изображения.
При его истечении в правом верхнем углу появляется перечёркнутый значок связи
размером 24×24 пикселя. Пиксели значка инвертируют исходный фон; чёрный становится
белым, белый — чёрным. Исходный буфер и его CRC не меняются. После подтверждения
актуальности исходная картинка восстанавливается точно, без следов значка.

В HA: **Настройки → Устройства и службы → GTag Display → Настроить →
Показывать значок устаревания через**. Значение задаётся в минутах, по умолчанию
15; 0 отключает контроль. Изменение вступает в силу после применения настроек
и успешной отправки нового кадра. Можно использовать и для макетов, отправленных
действием `gtag_ble_test.draw`: срок берётся из настроек этого экрана.

Ненулевой срок должен быть не меньше двух интервалов обновления, с округлением
вверх до целых минут. Например, при интервале 300 секунд минимальный срок —
10 минут, при 31 секунде — 2 минуты. HA не даст сохранить меньшее значение
и покажет необходимый минимум рядом с полем. При загрузке ранее сохранённых
настроек слишком короткий срок автоматически увеличивается до этого минимума;
значение 0 сохраняется. Новый срок применяется к плате при следующей успешной
отправке кадра.

HA периодически повторно вычисляет текущий макет. Если пиксели не изменились,
передаётся короткое подтверждение текущего кадра, примерно раз в треть заданного
срока. Если изменились — передаётся новое изображение с обычным ограничением
частоты обновления. Подтверждения неизменного кадра могут отправляться между
полными обновлениями. Ошибка шаблона или передачи нового кадра не продлевает
срок прежнего изображения.

Для `auto_update: false` и разовой отправки сырого изображения автоматических
подтверждений нет: через заданное время изображение помечается устаревшим.
Для постоянной таблички установите срок 0. Выбирайте срок с запасом относительно
интервала обновления и продолжительности Zigbee-передачи.

Датчик **Данные экрана устарели / Display data stale** позволяет строить
автоматизации. Пока первый кадр не подтверждён, состояние неизвестно.
В атрибутах указаны срок в секундах и последнее подтверждение. HA оценивает срок
по своим часам, консервативно от начала успешной операции; плата — независимо
по uptime с момента принятия кадра/подтверждения. Поэтому показания HA могут
опережать фактическое появление значка на длительность передачи. При остановке
HA значок на плате продолжит работать. В Zigbee2MQTT `frame_stale` позволяет
по запросу прочитать, показан ли значок на физическом LCD.

Срок относится к доставке и подтверждению изображения из HA. Он не определяет
возраст измерения исходного датчика. Готовые макеты показывают «—» для сущностей
`unknown`/`unavailable`; собственные шаблоны должны обрабатывать это явно.

## Обновление

Нужно согласованно обновить интеграцию, прошивку выбранного транспорта и, для
Zigbee, `gtag-display.mjs`. Изменять аппаратное подключение не требуется.
До публикации тега используйте готовые локальные UF2/ZIP из `dist/` либо локальные
`nrf-gtag-display.yaml` / `nrf-gtag-zigbee.yaml`. Конфигурации `gtag-ble.yaml` и
`gtag-zigbee.yaml`, закреплённые на новом GitHub-теге, заработают после его выпуска.

На плате нет постоянного опроса таймера в `loop()`: планируется одно пробуждение
к сроку истечения. LCD перерисовывается при появлении/снятии значка. Дополнительный
радиообмен подтверждений влияет на средний ток; новый средний ток ещё не измерен.

## Протокол

BEGIN теперь содержит дополнительные `freshness_timeout_s:u32` после CRC:
17 байтов для обоих транспортов, допустимый срок 0..86400 секунд. Срок входит
в описание сессии. Только первый успешный COMMIT запускает таймер; повторы
COMMIT и неудачные передачи его не продлевают. Старые короткие BEGIN по-прежнему
декодируются как срок 0, но для новой функции нужны все обновлённые компоненты.

Короткое подтверждение: `opcode:u8 | frame_id:u32 | raw_crc32:u32 | sequence:u32`,
13 байтов. BLE использует opcode 3 в прежней CONTROL-характеристике;
Zigbee — opcode 6. Sequence начинается с 1 и увеличивается для каждого нового
подтверждения в этой сессии. Повтор той же последовательности подтверждается,
но не переносит срок; меньшая последовательность, чужая сессия или CRC отклоняются.
После перезапуска платы подтверждение отклоняется, и HA повторно отправляет кадр.

Для Zigbee MQTT-команда `frame` принимает `{data, request_id, freshness_timeout}`.
Команда `frame_freshness` принимает `{frame_id, crc, sequence, request_id}`.
Ответы `freshness_*` имеют отдельный уникальный request ID; сохранённые MQTT-ответы
не подтверждают новый запрос. Радиоочередь использует `sendPolicy: immediate`.
