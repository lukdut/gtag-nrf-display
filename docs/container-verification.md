# Проверка HA Container и сборок на amd64 / arm64

Workflow [Container and native firmware](../.github/workflows/compatibility.yml)
проверяет установку интеграции в официальный HA Container и собирает прошивку
из YAML, скачанного в мастере этой установки. Каждая архитектура работает
на отдельной нативной Linux-машине GitHub Actions: `ubuntu-24.04` и
`ubuntu-24.04-arm`. QEMU и перенос готового SDK с другой машины не используются.

## Что проверяется

На каждой машине создаётся новая папка `/config`, без резервной копии,
`.storage` и установленных вручную Python-зависимостей. Интеграция распаковывается
из `gtag-ha-integration.zip`, собранного из проверяемого коммита.
Клиент тестирования и его зависимости находятся вне контейнера HA.

Проверка проходит через настоящие HTTP/WebSocket API Home Assistant, которыми
пользуется интерфейс:

1. Первоначальная настройка HA и создание пользователя.
2. Мастер прошивки до настройки MQTT: GPIO и батарея, скачивание YAML по
   подписанной ссылке до и после завершения мастера. Ссылка без подписи
   должна требовать авторизацию; фиктивная запись устройства не создаётся.
3. Настройка штатной интеграции MQTT, обнаружение GTag и создание сущностей.
4. Макет «Время и два показателя» с кириллицей, предпросмотр без отправки,
   применение, PNG 256 × 128 и обновление при изменении сущности HA.
5. Экспорт JSON, загрузка файла, замена исходной сущности при импорте,
   предпросмотр и применение.
6. Диагностика и «Проверить связь»: новый MQTT-ответ, понятная ошибка
   при имитации тайм-аута радио и успешная повторная проверка.
7. Перезапуск контейнера: сохранение макета и замены сущностей,
   восстановление MQTT и передача нового подтверждённого кадра.
8. Отсутствие ошибок, исключений и предупреждений GTag в журнале HA.

В стенде используется настоящий Mosquitto. Ответы Zigbee2MQTT/экрана имитируются
отдельным клиентом MQTT: радиооборудование GitHub Actions не требуется.
Тест не подменяет код HA или интеграции и не записывает настройки в `.storage`.

Этот сценарий обнаружил гонку при запуске HA: MQTT регистрирует локальный
обработчик раньше, чем завершает подписку у брокера. Кадр мог уйти в этот
промежуток, а быстрый ответ — потеряться. Перед командами интеграция теперь
дожидается готовности подписки на ответы. Ожидание ограничено тайм-аутом
команды и прерывается при отключении MQTT или выгрузке устройства.

## Сборка прошивки

После успешной установки скачанный YAML без изменений передаётся следующей
задаче той же архитектуры. В официальном контейнере ESPHome выполняется
полная команда `compile` с пустыми каталогами SDK и сборки.

Профиль: **Pro Micro / nice!nano, Zigbee, внешний делитель батареи**.
Проверяются архитектура контейнера, ELF-архитектура запущенного компилятора,
структура UF2, семейство nRF52840 и диапазон приложения от `0x26000`.
Результаты сборок не обязаны совпадать побайтно: пути и метаданные сборки
могут различаться между машинами.

YAML мастера закреплён на публичном теге прошивки. Поэтому отчёт отдельно
указывает коммит проверяемой интеграции, ссылку пакета прошивки и фактически
скачанные Git-ревизии пакета и внешнего компонента. Это не проверка всех
незарелизованных изменений C++ в текущей ветке.

## Версии и доказательства

- HA Container: **2026.9.2**.
- ESPHome Container: **2026.9.0**, nRF Connect SDK **2.9.2** из YAML.
- Mosquitto стенда: **2.0.22**.
- Прошивка: тег из YAML мастера, сейчас **v0.9.0**.

В разделе Actions конкретного запуска доступны артефакты:

- `ha-container-amd64`, `ha-container-arm64`: отчёт, журнал контейнеров,
  сведения об образе, скачанный YAML, экспортированный макет и PNG.
- `native-firmware-amd64`, `native-firmware-arm64`: UF2, исходный YAML,
  журнал сборки, сведения об образе и компиляторе, Git-ревизии и SHA-256.

Артефакты хранятся 14 дней. Папка конфигурации HA, пароли и токены владельца
в них не включаются. Для ручной проверки скачайте UF2 из нужного артефакта
и сверьте GPIO и параметры батареи перед записью на плату.

## Повторный запуск

В GitHub откройте **Actions → Container and native firmware → Run workflow**.
Проверка также запускается при изменении интеграции, конфигураций ESPHome
или самого стенда и входит в обязательные проверки выпуска.
Все задачи должны завершиться успешно.

Для локального запуска нужны Linux, Docker Engine с Compose, Python 3.12+
и свободные loopback-порты 18123 и 18883:

```bash
python3 -m venv /tmp/gtag-container-client
/tmp/gtag-container-client/bin/pip install -r tests/container/requirements.txt
PATH="/tmp/gtag-container-client/bin:$PATH" bash tests/container/run.sh
WIZARD_YAML="$PWD/dist/container-check/gtag-container-check.yaml" \
  PATH="/tmp/gtag-container-client/bin:$PATH" bash tests/container/build_firmware.sh
```

Для проверки arm64 эти команды должны выполняться на Linux arm64.
Стенд завершает свои контейнеры и сеть; временные каталоги `/tmp/gtag-container-*`
и `/tmp/gtag-build-*` после локальной проверки можно удалить.

## Границы результата

Успех CI подтверждает работу установочного ZIP и API интеграции в HA Container
на двух архитектурах и сборку выбранного профиля прошивки на них.
Он не подтверждает прохождение установки через HACS, клики в браузере,
физическую радиосвязь или работу конкретного Bluetooth-адаптера.

Отдельный ручной прогон: установить интеграцию через HACS в чистой виртуалке,
подключить существующий Zigbee2MQTT, записать UF2 из ARM-сборки на целевую плату,
проверить изображение, диагностику и обновления после перезапуска HA Container.
Управляющую запись этого экрана в основном HA на время прогона отключают.
